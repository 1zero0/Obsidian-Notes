# 周末作业 · 用例设计方法的使用（预习笔记）

日期：2026-10-17　姓名：薛宇璇　课程：游戏测试培训

> 本次预习的重点是「怎么用」——每种方法解决什么问题、按什么步骤操作、最后怎么落成一条条能被别人执行的用例，并配课上的活动案例举例。

---

## 一、先立个框架，不然方法记不住

**三个层次不能混：**

| 层次 | 回答什么 | 产出 |
|---|---|---|
| 需求 | 策划要做什么 | 需求文档 |
| 测试点 | 要测什么 | Xmind 测试点 |
| 测试用例 | 用什么数据、怎么操作、预期是什么结果 | 用例表／用例库 |

用例设计方法是**第三层**的工具：它不负责"找出要测什么"（那是需求分析的事），它负责在已经确定要测的地方，**选出最容易暴露缺陷的那几组数据**。

**核心矛盾：要覆盖得住，又要用例不冗余。** 穷举不可能（一个输入框就有无穷多种填法），方法的价值就是——用尽量少的用例，挡掉尽量多的风险。

**一条合格的用例必须能被别人照着执行**，四要素缺一不可：前置条件、操作步骤、输入数据、预期结果。最容易写虚的是"预期结果"：不要写"正常显示"，要写"按钮置灰，下方提示『今日已签到，明天再来』，奖励不重复发放"。

本次六种方法都是**黑盒**方法；白盒那套（语句覆盖、判定覆盖、条件覆盖、判定/条件覆盖、条件组合覆盖、路径覆盖、MC/DC）先放一边。

## 二、六种方法逐个拆

### 1. 等价类划分

**本质**：把输入域切成若干「等价类」，同一类里取任何一个值，揭露缺陷的效果相同——所以每类只取一个代表值就够了。

分两类：**有效等价类**（合理的、应该被接受的输入）、**无效等价类**（不合理的、应该被拒绝的输入）。

**使用步骤**：
1. 找出功能里所有可以被输入／触发的条件（等级、数量、次数、时间点、状态……）；
2. 对每个条件分别划有效类、无效类，编上号；
3. 写用例：
   - **有效类**：一条用例尽可能多覆盖几个有效类（有效类之间通常不互斥）；
   - **无效类**：一条用例**只覆盖一个**——一次只犯一个错，才能确定这回报错是哪个原因引起的。一次填错好几个，报错分不清是谁的锅，等于白测。

**举例**（签到活动的参与资格）：

| 输入条件 | 有效等价类 | 无效等价类 |
|---|---|---|
| 角色等级 | ① ≥6 级（取 6、30） | ② ≤5 级（取 0、1、5） |
| 每日赠送时装次数 | ① 1~10 次 | ② 0 次（未赠送）　③ ≥11 次 |
| 翻牌消耗的积分 | ① 积分 ≥ 单次消耗 | ② 积分 < 单次消耗（含 0、负数） |

**易错点**：
- 按业务规则的取值边界划类，不是按"我随便分几档"划；
- 无效类要想着"玩家能怎么坏"：负数、超大值、空值、小数、全角字符——这些从 GM 工具／后台改数据时特别容易漏。

### 2. 边界值分析

**本质**：缺陷最爱躲在边界上，边界附近的缺陷密度明显高于区间中间。

**使用步骤**（先做完等价类再做这个）：
1. 找出每个等价类的取值区间；
2. 在区间两端取点：
   - 基础取法（4n+1）：`min`、`min+`、`正常值`、`max-`、`max`
   - 健壮性取法（6n+1）：再加 `min-`、`max+`
3. 每个取值点至少一条用例。

**举例**：

| 被测点 | 边界取值 |
|---|---|
| 等级门槛 ≥6 级 | 5、6、7 级（min-、min、min+） |
| 赠送时装上限 10 次 | 9、10、11 次（max-、max、max+） |
| 拼图总块数 N（按配置表） | 翻开第 N-1、N、N+1 次（第 N+1 次应提示已翻完、不扣积分） |
| 活动时间 8/1 00:00 – 8/6 23:59 | 7/31 23:59:59、8/1 00:00:00、8/6 23:59:59、8/7 00:00:00 |
| 单次翻牌消耗积分 | 差 1 分（不够）、刚好够、刚好多 1 分 |

**易错点**：
- 时间边界要区分客户端时间／服务器时间，还要测跨天、跨月、活动结束后；
- 数量的边界必须包含 `0` 和「上限 +1」，不能只取 max。

### 3. 错误推断法（错误推测法）

**本质**：凭经验和直觉猜哪里会出错。没有公式、不可穷举，靠积累，所以叫经验法。

**它的位置**：等价类／边界值／判定表／因果图覆盖的是"规则内"，错误推断覆盖的是"规则外的骚操作"——线上真正的坑多半出在这里。

**可以直接背走的弹药清单（游戏测试版）**：

1. **脏数据**：空/不填、0、负数、超大值、小数、全角半角、中英混排、特殊符号 `%&#@`、Emoji、前后空格、超长文本（昵称／聊天／公会名）
2. **重复与并发**：连点按钮、重复提交、快速返回再进入、同一账号多端登录、多人同一时刻抢同一资源
3. **网络与环境**：断网、弱网、切后台、杀进程、飞行模式、来电打断、服务器重启
4. **时间**：改本地时间刷签到、跨天、活动开始前一秒／结束后一秒、服务器与客户端时间不一致
5. **容量与上限**：背包满、邮件满、道具已达上限、金币溢出为负、等级满级
6. **状态错位**：活动进行中下架活动、活动结束后再操作、被封号/禁言状态下操作、签到前后等级发生变化
7. **账号与渠道**：不同区服、不同渠道包、iOS／安卓、游客号、未实名、未成年账号

**举例**：签到成功后立刻把手机系统时间改成明天，看能不能再签一次（防刷）；1 秒内连点"签到"10 次，看奖励是否只发一次（幂等）。

**易错点**：它是**补充**手段，不能当主方法——它只保证"我想到了"，不保证"覆盖全了"。

### 4. 判定表

**本质**：把"多个条件组合出什么结果"列成一张不漏项的表格。适合**业务规则型**需求（要不要发、发哪个、给什么提示）。

**四个部分**：条件桩（有哪些条件）、动作桩（能做什么动作）、条件项（各条件取值 Y/N）、动作项（该组合下执行哪个动作）。

**使用步骤**：
1. 数出条件个数 n → 列出 2ⁿ 种组合（这就是"不漏"的保障）；
2. 把不影响结果的条件合并为 `-`（无关项），化简表格；
3. 化简后的每一条规则（也就是每一列）→ 至少一条用例。

**举例 1**：签到按钮——点了会发生什么。

条件：C1 角色等级 ≥6；C2 在活动时间范围内；C3 今日已签到。

| | R1 | R2 | R3 | R4 |
|---|---|---|---|---|
| C1 等级 ≥6 | N | Y | Y | Y |
| C2 活动期内 | — | N | Y | Y |
| C3 今日已签到 | — | — | Y | N |
| A1 提示"角色等级未达 6 级，暂不能参加" | ✓ | | | |
| A2 入口置灰／提示"活动未开始／已结束" | | ✓ | | |
| A3 按钮置灰，提示"今日已签到，明天再来" | | | ✓ | |
| A4 签到成功，发放当日奖励，状态改为已签到 | | | | ✓ |

8 种组合化简成 4 条规则 → 4 条用例，既没漏也没冗余。

**举例 2**：翻牌——点了会发生什么。

条件：C1 亲密度积分 ≥ 单次消耗；C2 该拼图块此前已翻开过。

| | R1 | R2 | R3 |
|---|---|---|---|
| C1 积分足够 | N | Y | Y |
| C2 该块已翻开过 | — | N | Y |
| A1 弹提示"没有足够的亲密度积分，赶快与好友一起组队赚积分吧"，不扣积分不翻牌 | ✓ | | |
| A2 扣积分 + 翻开 + 基础奖励 + 拼图奖励（该块首次） | | ✓ | |
| A3 扣积分 + 翻开 + 只有基础奖励 | | | ✓ |

**易错点**：
- 条件之间有依赖时（例如"账号不存在就不用校验密码"），判定表会显得别扭——先用因果图把约束画清楚，再转成判定表；
- 化简成 `-` 时要确认"这条条件真的不影响结果"，化简错了就是漏测。

### 5. 因果图

**本质**：判定表解决"组合"，但解决不了"条件之间有依赖"。因果图先把**因（输入）**和**果（输出）**画出来、标清约束，再**转成判定表**出用例——所以因果图不是终点，它的产物就是判定表。

**五种约束符号**：

| 符号 | 位置 | 含义 |
|---|---|---|
| E（互斥） | 因之间 | 最多只有一个成立 |
| I（包含） | 因之间 | 至少有一个成立 |
| O（唯一） | 因之间 | 有且仅有一个成立 |
| R（要求） | 因之间 | a 成立，则 b 必须成立 |
| M（屏蔽） | 因→果、果→果 | a 成立，则 b 必不成立 |

**步骤**：① 从需求里找出所有因和果；② 标示约束；③ 画因果图；④ 转判定表；⑤ 每条规则出用例。

**举例**（登录）：
- 因：c1 账号存在、c2 密码正确、c3 账号已封禁
- 果：e1 登录成功、e2 提示"账号不存在"、e3 提示"密码错误"、e4 提示"账号已被封禁"
- 约束：c2 对 c1 是 **R**（账号不存在，就不必谈密码是否正确）；e1 与 e2/e3/e4 是 **E**（互斥）
- 转判定表 → 4 条用例

**游戏里的用法**：活动规则的"因"常常成串——"积分够 + 在活动期 + 未领过"才发奖励，而"积分够"本身有前置（先完成任务才有积分）。这种带前置依赖的规则，用因果图理顺最省事。

### 6. 流程图（场景法）

**本质**：沿业务流程走一遍。**基本流**（理想路径）只有一条；只要走不到基本流，全是**备选流**（正常分支 + 异常分支）。

**步骤**：
1. 画出主干流程图（椭圆=开始/结束，矩形=事件，菱形=判断）；
2. 基本流：1 条用例走通；
3. 备选流：每条单独出用例（"基本流 + 某个备选流"）；
4. 备选流组合：2 个以上叠加，测复杂场景（例如"漏签 + 补签 + 补签算不算连续"）。

**举例**：亲密度积分活动主流程——

组队比赛／完成任务 → 获得亲密度 → 按比例转成积分 → 到兑换界面翻牌 → 得基础奖励（首次翻开额外得拼图奖励）。

备选流：
- 积分不足 → 弹提示、不扣积分、不翻牌；
- 翻到已翻开过的拼图 → 只给基础奖励；
- 赠送次数达上限 → 不再获得积分；
- 活动期结束／中途下架 → 入口状态与已得积分如何处理。

如果画的是状态机，那就是**状态迁移测试**：签到状态「未开启 → 待领取 → 已领取 → 已过期」，逐个验证"当前状态能做什么操作、做完变成什么状态、能不能回退"（能回退就是 BUG）。

**易错点**：场景法看的是"流程"，等价类／边界值看的是"数据"，两者互补——跑流程时每一步的数据照样要用边界值。

## 三、补充第七种：正交实验法

条件一多，判定表就 2ⁿ 爆炸（5 个条件 = 32 条）。正交实验法（两两组合／Pairwise）用"任意两个条件的取值组合至少出现一次"的规则，把用例数量压得很小，代价是不保证三条件以上的组合覆盖。

适用：多参数配置类——机型 × 系统版本 × 网络 × 分辨率 × 渠道包（适配测试的经典用法）。

## 四、方法之间的关系：什么时候用哪一个

| 需求长什么样 | 首选方法 | 配合 |
|---|---|---|
| 有取值范围、有枚举（等级、数量、次数） | 等价类 + 边界值 | 错误推断补脏数据 |
| 多条件组合决定一个结果（发不发、给哪个提示） | 判定表 | 条件有依赖先画因果图 |
| 条件之间有依赖／约束 | 因果图 | 转判定表出用例 |
| 有先后顺序、跨模块的业务流程 | 流程图／场景法 | 每步的数据仍用等价类 + 边界值 |
| 状态会变化的系统 | 状态迁移测试 | 场景法 |
| 参数组合爆炸（适配／配置） | 正交实验法 | — |
| 以上全部 | 错误推断兜底补漏 | — |

一句话串起来：

```
单变量取值  → 等价类 ──配对──> 边界值
多条件组合  → 因果图 ──转换──> 判定表
有流程/状态 → 流程图 ──扩展──> 场景法 / 状态迁移
全部之上    → 错误推断（经验补漏）
```

## 五、综合演练：把《七日征程·荣耀加冕》拆成用例

用课上看过的那份需求，练一遍"方法怎么用"。

### 5.1 先出测试点（这一步是需求分析，不是用例设计方法，但没有它后面无从下手）

活动时间（开始／结束／刷新点）｜参与对象（角色等级 ≥6、中途升到 6 级算不算）｜活动入口（活动中心、登录弹窗）｜每日签到｜连续签到与额外奖励｜补签（条件、获取方式、上限、使用限制、生效效果）｜奖励发放（入包还是邮件、背包满）｜成就彩蛋（称号限时、头像框永久）｜红点与状态显示｜分享得补签卡。

### 5.2 用等价类 + 边界值做「签到准入」

| 输入条件 | 有效等价类 | 无效等价类 | 边界值 |
|---|---|---|---|
| 角色等级 | ≥6 级 | 0~5 级 | 5、6、7 |
| 活动时间 | 8/1 00:00 ~ 8/6 23:59 之内 | 之外（开始前、结束后） | 7/31 23:59:59、8/1 00:00:00、8/6 23:59:59、8/7 00:00:00 |
| 今日签到次数 | 0 次（未签） | 1 次（已签） | 0、1 |

### 5.3 用判定表做「今天点签到，会发生什么」

→ 见第 4 节的判定表 R1~R4，直接转成 4 条用例。

### 5.4 用场景法做「漏签 → 补签」全流程

- 基本流：连续签到第 1、2、3 天，每天都正常发奖励；
- 备选流 1：第 2 天未登录漏签 → 第 3 天登录 → 补签第 2 天 → 验证是否计入连续、是否补发当天奖励、第 3 天奖励是否正常；
- 备选流 2：没有补签卡 → 点补签 → 提示获取方式，不消耗资源；
- 备选流 3：本次活动已用过 1 次补签 → 再点补签 → 提示次数已用完。

### 5.5 用例样例（节选）

| 编号 | 测试点 | 前置条件 | 操作步骤 | 预期结果 | 设计方法 |
|---|---|---|---|---|---|
| 签到-01 | 等级刚好达标可参与 | 角色 6 级，活动期内，今日未签到 | 打开活动中心 → 点签到 | 签到成功，发放第 1 天奖励，按钮变为已签到 | 边界值（min） |
| 签到-02 | 等级不足不可参与 | 角色 5 级 | 打开活动中心 | 入口不显示或置灰，提示等级不足 | 边界值（min-） |
| 签到-03 | 重复签到 | 6 级，今日已签到 | 再次点击签到 | 按钮置灰不可点；若能点则提示"今日已签到"，奖励不重复发放 | 判定表 R3 |
| 签到-04 | 活动开始瞬间 | 6 级，服务器时间 8/1 00:00:00 | 点签到 | 可签到（整点归属需与策划确认后核对） | 边界值（时间 min） |
| 签到-05 | 活动结束后 | 6 级，服务器时间 8/7 00:00:00 | 打开活动中心 | 活动入口关闭，不可签到 | 边界值（时间 max+） |
| 签到-06 | 连续签到额外奖励 | 已连续签到 2 天 | 第 3 天签到 | 发第 3 天奖励 + 英雄碎片×2，进度条显示"已连续 3 天" | 场景法（基本流） |
| 签到-07 | 漏签后补签 | 第 2 天未登录，持有补签卡 | 第 3 天点补签 | 补签卡 -1，补发第 2 天奖励；"是否算连续"按策划确认结果核对 | 场景法（备选流） |
| 签到-08 | 无补签卡 | 未分享过，无补签卡 | 点补签 | 提示补签卡的获取方式，不消耗任何资源 | 判定表／错误推断 |
| 签到-09 | 连点防重 | 6 级，今日未签到 | 1 秒内连点签到 5 次 | 只发一次奖励，无重复入包、无报错 | 错误推断 |
| 签到-10 | 改时间防刷 | 今日已签到 | 把手机系统时间改为明天后点签到 | 以服务器时间为准，仍提示已签到、不可签 | 错误推断 |
| 签到-11 | 背包满 | 背包已满 | 点签到 | 奖励转入邮件（或按需求给出明确提示），不丢失 | 错误推断 + 需求澄清 |
| 签到-12 | 奖励到账核对 | 任意合法账号 | 签到后查看背包 | 道具名称、数量、有效期与配置表一致 | 配置表核对 |

> 预期结果里凡写着"按策划确认"的，就是 10.15 需求分析里已经提出的疑问点（补签算不算连续、整点能不能签、背包满怎么办……）。**需求没定死的地方，用例不能自己编，要标记为阻塞并等评审结论**——这是老师反复强调的"不能用我觉得代替策划的规则"。

### 5.6 小结（我理解的"使用"）

方法不是挨个用的清单，而是**看需求长什么样，挑对应的那一个**：

1. 先看有没有范围和枚举 → 等价类 + 边界值；
2. 再看有没有多条件组合 → 判定表（条件有依赖就先画因果图）；
3. 再看有没有流程和状态 → 场景法／状态迁移测试；
4. 最后拿自己的经验清单扫一遍脏数据、并发、时间、容量 → 错误推断；
5. 组合爆炸就上正交实验法。
