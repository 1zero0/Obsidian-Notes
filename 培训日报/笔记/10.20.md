## 测试流程：测试每天要做的：
### 测试准备阶段：
10.1开始，开发会开发新需求出来，到10.10（第二周：完成测试准备），每天在TAPD搜集新需求，并将需求上传到需求文档，并在测试人哪儿写自己名字；开始对自己负责的需求进行分析评审，有问题找策划开发进行评审解决掉；整理成测试点/测试用例，并且对测试用例进行评审；整个版本的所有需求都需要完成以上的要求，在完成测试准的时候要全部完成
准备工作出了需求分析，设备，用例，环境，
### 测试阶段
如果在开发第一周10.17之前就有开发好的功能，就可以直接开始测试，一定是**用例准备好**的情况下
每天都在打包，打完包以后就需要**冒烟测试**，从10.1到10.10的两周可以不进行冒烟；冒烟是做什么，是去验证包能不能用，为测试准备打好基础
冒烟从10.10开始到封板提审这一天；冒烟过程中如果有需求转测了，就可以开始测试（详细测试），优先级那个高先测那个，第一个需求不能测可以先继续测后面的，不要等待开发，持续不断地测试
测试出BUG就要按规范提BUG，提交后就需要跟进BUG的修改情况，BUG修好后就需要回归
除了测试已经有的，还要注意有没有需求转测，也要推进这个需求转测
### 遇到困难
在整个测试周期内遇到了困难，或者有些问题解决不了，反馈风险，将这些事发给组长，如果组长解决不了让PM去推进；每天书写日报，进行风险的反馈；不能让事情砸在我们手里
工作量太大，不是一个人能解决的或者遇到问题没办法自己解决，就找组长，申请加班，找上级领导解决问题。
### 测完准备封板提审
需要做一次全量测试，保证送审的这个包质量要过关
预发布服：再做一遍测试；因为服务器和环境变了，需要做二次检查；**能测的功能**再测一遍，正式配置有些功能还没开放，所以有些功能没办法测，或者有些工具/条件需要一些工具配合才能测
全量测试的时候有BUG就要用热更进行BUG修改，用热更将修改好的BUG/需求传到最终包中；用热更也要遵守规则，先在测试服测试，测试服没问题用热更新的方式更新到预发布，预发布服测试没问题再用热更新更新到正式服，
正式服最终会有三个：包+热更+资源
预下载：新版本的资源可以直接下载

# 测试点专门写？怎么把测试点转成测试用例？
预习：从【验什么】到【怎么验】
- **测试点**：需要被验证的**一个关注点**，回答“验什么”，一条一句话，不含具体数据、不含操作步骤。
- **测试用例**：把测试点**具体化**成可执行、可判定的步骤，回答“怎么验”，含前置条件、数据、步骤、预期结果。

## 测试用例的编写
### 测试点
**测试点概念：测试过程中需要检查的具体位置或方面**
解析：测试点是你测试时的“核心关注项”，帮你明确“该测什么”，即要检查的“关键点”
排行榜：
	排行榜解锁：等级要求
	
**测试用例的概念：测试过程的详细规划，包含输入数据、操作步骤和预期结果等要素。**
解析：测试用例是把测试点变成了可操作的步骤，帮你明确“怎么测”“测了之后要什么结果”。

| 用例编号 | 所属模块 | 用例描述 | 前提条件     | 操作步骤                        | 预期结果       | 实际结果     | 优先级 | 备注  |
| ---- | ---- | ---- | -------- | --------------------------- | ---------- | -------- | --- | --- |
| 1    | 排行榜  |      | 角色等级>=30 | 查看排行榜是否解锁                   | 1.解锁成功     | Pass/通过  |     |     |
|      |      |      |          | 检查UI1.去xxx检查入口2.用3.点击入口按钮查看 | 1.入口加锁图标消失 | Pass<br> |     |     |
|      |      |      |          |                             |            |          |     |     |
用例要素：
1.用例编号
2.所属模块：属于哪个功能模块的
3.用例描述：要测这个模块的那个功能点
4.前提条件：测这个功能点应该有什么前提准备
5.操作步骤：根据
6.预期结果：需求设计的目的
7.实际结果：根据前面测试后游戏实际表现是什么；1.Pass/通过；2.Fail/失败，失败后要提BUG；3.NA（代表未测/当前无法测试）在备注上写明原有
8.优先级：用例的重要性；P0、P1、P2、P3、P4；低挡：文字类；中档：界面UI类；
9.备注：
### 用例类型
1.全功能用例
是指涵盖要测试对象（某游戏、软件）的所有功能的测试用例。就是对整个系统进行测试，该用例宝库偶所有的正常流程、异常分支、交互模块等测试点
2.通用用例
同游戏不同模块都包含的功能，这些功能的测试点基本一样，所以总结出一份都可以使用的用例，称为通用用例。
3.最小检查点
包含功能的基本功能、易出现bug点。一般在除第一次的迭代版本、回归版本的时候执行测试，保证功能正常。
就是所有功能里面的一个点
4.冒烟用例
冒烟测试用例选用全功能用例中的基本重点功能（核心功能点）测试。
5.专项用例
主要是指手机游戏的专项测试用例。包括兼容性测试用例、中断测试用例、前台性能测试用例、弱网测试用例
# 测试用例设计流程
1. 要对功能或需求绝对的熟悉和理解
2. 要懂得如何拆解功能（核心：从大往小拆，拆到无法拆为止；一个大功能，拆成一个个单独能玩、单独能测的小动作、小效果，每一个小项就是功能点）
3. 要学会使用用力编写方法。
备注：不管是设计测试用例还是测试点，拆解功能点时要拆到无法拆为止，其次不管是一条还是一个测试点，只对应一个可测试功能点。
# 测试点拆解
**方法1：按【操作步骤】拆分（场景法）**
适用：玩法、任务、交互、弹窗、背包、商城、技能等绝大多数游戏功能
拆分逻辑：跟着玩家点击/操作顺序一步步拆，点一下=一个功能点。
口诀：先做啥，在做啥，最后出啥效果
举例：
忍者应援：活动开始时间，参与条件，活动入口，活动界面（前端设计的UI效果），获取应援券（登录，对局，邀请助力），应援，活动奖励，应援记录，红点提示
这些就算1级测试点
活动时间：开始，结束，投票结束，刷新
任务：去完成，完成，已完成，可领取，已领取
**方法2：按【页面/模块区域】拆分（适合界面类功能）**
适用：主界面、背包、角色面板、设置、排行榜、聊天页面等多区域界面。
拆分逻辑：把一整个大页面、按不同区域
**方法3：按【状态/场景】拆分（适合有多种情况的功能）**
适用：角色状态、技能、buff、关卡、胜负逻辑、组队、匹配逻辑拆分逻辑：同一个功能、不同情况、不同状态拆分开拆、每种状态算一个点。
举例：【角色血量显示】拆分功能点：
1. 满血状态显示正常
2. 掉血后数值/血条同步变化
3. 血量归0（死亡）状态展示正确
4. 回血时血条/数值上涨正常
方法4：按【正向+异常】拆分
正向功能：玩家按设计流程、规规矩矩操作，网络、界面、数据都正常，是功能的标准使用流程。
异常功能：不按设计流程操作、玩家误操作、乱点、操作被打断、数据触达极限、网络出问题等非标准、意外场景，也是BUG重灾区
# 用例设计方法
1、等价类划分法
等价类是指某个输入域的子集合（某个功能条件的集合）。可以把全部输入的数据合理划分为若干等价类，在等价类中选取一个数据作为测试输入条件，就可以用于少量代表性的测试数据。
例子1：副本，进入副本时有要求，角色等级>100（功能的条件）,战力>=5000,职业：不要辅助（射手，战士，法师）
等价类：角色等级：101-等级上限；战力：5000-战力上限，职业：{射手、战士、法师}
非等价类：角色等级0-100，角色等级＜0；战力：0-4999、战力＜0、战力为空（null）；职业：辅助、未选择职业

例子2：有一个图书管理系统，可以查询1949-2026年内的图书，查询方式需要手动在输入框输入事件，前四位代表年，后两位代表月，设计等价和非等价
等价类：年：1949-2026，月：01-12；示例：200302
非等价类：年：＜1949，＞2026，月：＜01，大于12；特殊输入：不满6位，超过6位，非数字，不输入，示例：194805；202701；2024；20250109；二零二五零三；

输入框的需求：年份：1949-2026；月份：01-12；长度等价：6
非等价：非数字类型，大于6小于6，

等价类：可以满足功能条件范围的就叫等价类，然后从中选取典型
非等价类：不满足条件的部分
功能判定：角色装备穿戴、攻击目标判定、释放范围判定
