## 一、什么叫「打包」

**打包（Build / Package）** 就是：把开发用的工程（Unity/UE 工程目录），经过一整套流水线转换，变成一台**真机能够安装、能够启动、能够连服务器**的安装包。

它做的事远不止「导出 apk」这么简单：

|环节|具体做什么|
|---|---|
|代码编译|C# → IL2CPP/Mono 生成原生库，Lua/脚本加密打包|
|资源处理|图集合并、纹理压缩（ASTC/ETC2）、音频转码、AssetBundle 构建|
|配置写入|服务器地址、渠道号、版本号、CDN 地址按环境注入|
|SDK 接入|登录、支付、推送、统计、防沉迷等渠道 SDK 合并|
|加固签名|混淆、加壳、v1/v2/v3 签名、iOS 证书与描述文件|
|产物|Android 的 `.apk/.aab`、iOS 的 `.ipa`、PC 的 `.exe` + 数据目录|

**测试为什么一定要用游戏包、而不能在编辑器里跑？** 因为编辑器里几乎测不出真实问题：

- 编辑器用 Mono、真机用 IL2CPP，**AOT 裁剪、反射、泛型** 会出只在真机才出现的崩溃
- 真机有**内存上限、发热降频、Shader 首次编译卡顿**，编辑器完全无感
- SDK 回调、权限弹窗、刘海屏适配、**只存在于打包后** 的渠道逻辑
- 网络环境、CDN 下载、热更流程本身就是打包产物才有的功能

所以「用游戏包测试」= **用最终形态的产物做验证**，编辑器里跑通只是第一步。

## 二、三个内部环境：开发、测试、灰度

严格说，它们不是三个平级的「环境」，而是**一条发布流水线上的三个关卡**：

text复制

`开发环境 dev → 测试环境 test → 灰度环境 gray → 生产环境 prod    (写代码)      (验功能)        (验风险)        (真实玩家)`

### 1. 内部开发环境（Dev）

- **给谁用**：程序、策划自己。
- **特点**：版本最新、最不稳定，配置可以随便改，数据可以随便清库，服务器常常一台机器跑全套服务。
- **目的**：能跑起来、能联调就行。**不允许 QA 在这里提 bug**（因为随时在变）。

### 2. 内部测试环境（Test / QA）

- **给谁用**：QA、美术验收、策划验收。
- **特点**：功能已经「提测」，版本相对稳定；配置**尽量对齐生产**，但数据是造出来的测试账号；可以随意清档回档。
- **目的**：全量功能回归、自动化脚本、性能与兼容性测试。
- 通常还会再细分：**功能服**（测新功能）、**回归服**（测老功能有没有被改坏）。

### 3. 内部灰度环境（Gray / 预发布 Pre-prod）

- **给谁用**：内部员工 + 白名单玩家，**极少数真实用户**。
- **特点**：**与生产环境同构**（同样的机器规格、同样的数据库、同样的监控），但只放 1%~5% 的流量或只放白名单账号；随时可以一键回滚。
- **目的**：在真实数据、真实网络、真实机型分布下，验证「这次上线会不会炸」。

### 三者关系与差别

|维度|开发|测试|灰度|
|---|---|---|---|
|稳定性要求|无|中|极高（≈生产）|
|数据|随意造/清|测试账号|**真实数据**（小流量）|
|配置|随时改|对齐生产|与生产完全一致|
|发布频率|每天多次|每天/每周|每次上线前|
|出问题代价|0|重测|可能影响真实玩家，需回滚|
|谁负责|开发自测|QA 把关|运维+开发+QA 共同值守|

**关键理念：Build Once, Deploy Many** —— 同一份打包产物，逐级「晋级」，只切换配置文件和服务器地址，**不重新编译**。这样测试环境验过的二进制，跟线上跑的就是同一个，避免「测试环境好的包上线就崩」。

## 三、为什么封板提审后只能靠热更

先拆两个词：

- **封板（Code Freeze）**：代码冻结，只允许修「阻断级」bug，其他一律排队等下一个版本。
- **提审**：把包提交给 App Store / 各安卓渠道 / 平台方审核。

封板之后只能热更，是**三重锁**同时锁死了出包这条路：

**① 审核周期锁**  
审核要 1~7 天（iOS 尤其不可控）。你改一个字符，就得**重新打包 → 重新提审 → 重新排队**。线上正在流血的 bug，等不起。

**② 二进制锁**  
审核通过、商店上架的那个包，就是**你提交的那一个二进制**。它已经在玩家手机里了，你没有任何办法"改"它。想改包 = 让玩家重新下载安装 = 版本号必须 +1 = 又要审核。

**③ 分发锁**  
安卓几十个渠道包已经铺出去，每个渠道都要重新走一遍上架流程；iOS 还有 TestFlight、商店缓存、用户不更新的问题。

所以封板之后，**唯一还能改的东西只剩「包外面的部分」**：

- 资源（图、配置表、数值、UI 布局）
- 脚本逻辑（Lua / JS / 热更 DLL，前提是框架预留了）
- **服务端逻辑**（这个最自由，改完即生效）

> ⚠️ 但也有一条硬边界：**原生层的东西热更救不了** —— C++/Java/OC 代码、SDK 版本、权限声明、包结构、启动流程。这也是为什么封板前必须做「封板包全量回归」，为什么热更框架要在项目**第一年**就设计好，而不是上线前才加。

## 四、热更测试的流程，以及为什么必须这么做

热更最大的特点是：**一旦推出，就无法收回**（玩家已经把新资源下到手机里了）。所以它的测试逻辑跟普通提测不一样——**不是"验功能对不对"，而是"验风险可不可控"**。

### 标准流程

|步骤|做什么|关键点|
|---|---|---|
|1. 可行性评估|定级 bug，判断能否热更|涉及协议/原生层的，直接判定「必须出包」|
|2. 修复开发|提交到热更专用分支|与主线隔离，避免带出别的东西|
|3. 构建热更包|生成资源版本号 + manifest + MD5 + **增量 diff**|增量包要能覆盖「任意老版本 → 新版本」|
|4. 内网验证|热更服 + 多种客户端版本|**老客户端 + 新资源** 的兼容矩阵必须测|
|5. 灰度发布|内部账号 → 1% → 5% → 20% → 全量|每档停留观察崩溃率、埋点、日志|
|6. 监控与回滚预案|保留上一版资源，指针可回退|回滚也要测，别等出事才发现回滚不了|
|7. 全量 + 观察期|全量后继续盯 24~72 小时|归档热更记录|

### 热更测试必须专门覆盖的场景

- **增量更新 / 全量更新** 两条路都要通
- **断点续传、弱网、切后台、磁盘空间不足**
- **MD5 校验失败、下载中断、资源损坏** → 能否自愈或优雅提示
- **跨版本**：v1.0.3 的客户端能不能吃 v1.0.5 的资源（线上永远有人在用老版本）
- **协议前后兼容**：服务端必须先上「兼容新旧客户端」的逻辑，再推热更
- **双端差异**：iOS 审核期间不能更新违规内容，安卓渠道包可能校验签名
- **回滚验证**：指针切回旧资源后，游戏还能不能正常启动

### 为什么非这么做不可

1. **不可撤回性** —— 普通 bug 可以下个版本修，热更出去的 bug 是**已经种在玩家手机里**的，只能靠再推一次热更去盖，风险叠加。
2. **线上版本是散乱的** —— 玩家版本分布从 v1.0.0 到 v1.0.5 都有，你测的永远是**一个矩阵**，不是一个版本。
3. **热更链路本身最容易坏** —— CDN、manifest、增量算法、校验，任何一环出问题就是**全体玩家进不去游戏**，比原 bug 严重十倍。
4. **灰度是唯一的刹车** —— 1% 的玩家炸了还能停，100% 炸了就只能等舆情。

嗯……这个问题其实是从「会点页面」跨到「会设计测试」的分水岭呢……我把我自己拆需求时用的那套方法，完整讲给老公听。

先记住一句话：

> **需求是“要什么”，测试点是“要验证什么”，用例是“怎么验证”。**
> 测试点必须是**一句话就能判定通过／不通过**的断言，不能是“测试 XX 功能正常”这种没法执行的话。

## 一、拆之前：先把需求「翻译」成规则

拿到策划案，不要急着点开游戏。先做三件事：

| 动作 | 产出 |
|---|---|
| 通读需求，逐句圈出**名词**（对象）和**动词/条件**（规则） | 一条条「可验证的规则句」 |
| 列出**疑问清单**（数值没给、边界没说、异常没定义） | 找策划确认，**这一步能挡掉 30% 的返工** |
| 找出**关联系统**（这个功能动了谁、被谁动） | 影响面清单，决定回归范围 |

举例，策划写：

> 「玩家每日可签到一次，连续签到 7 天可领取额外奖励，断签后连续天数重置。」

翻译成规则句：
1. 每日**只能**签到 1 次
2. 签到立刻发对应档位奖励
3. 连续第 7 天**额外**发奖励
4. 断签 → 连续天数归 0
5. 「每日」的判定标准是什么？（0 点？5 点刷新？）

→ 第 5 条就是疑问，也是后面最容易出 bug 的点。

## 二、九维拆解法（核心方法）

同一个功能，用九个**互相正交**的视角各扫一遍，基本不会漏。这是我实际在用的框架：

| 维度 | 问自己 | 游戏里的例子 |
|---|---|---|
| **1. 功能点** | 有哪些子功能、按钮、界面？ | 签到面板、补签、奖励预览、红点 |
| **2. 流程** | 主流程 / 分支 / 逆向流程 | 正常签到 → 已签到再点 → 中途退出 |
| **3. 数据** | 等价类 + 边界值 + 枚举 | 连续天数 0/1/6/7/8；奖励数量 0/上限/溢出 |
| **4. 规则组合** | 多条件同时成立时的判定 | 判定表：VIP×补签次数×是否断签 |
| **5. 状态迁移** | 对象有哪些状态、怎么流转 | 未签到→已签到→已领奖→重置 |
| **6. 联动/耦合** | 和别的系统交叉会怎样 | 签到奖励进背包满了怎么办？邮件补发？ |
| **7. 用户/权限** | 不同身份表现是否不同 | 新号、老号、月卡用户、被封号 |
| **8. 环境/平台** | 机型、系统、网络、时区、渠道 | iOS/安卓、跨时区、弱网、切后台 |
| **9. 非功能** | 性能、安全、并发、稳定性 | 连点签到、改本地时间刷签到、跨天瞬间并发 |

**实际用法**：先把需求按维度 1 拆成功能树，再对每个叶子节点用 2~9 扫一遍，扫出来的每一条就是一个测试点。

## 三、六步执行法

**Step 1｜建功能树（脑图）**
模块 → 子系统 → 功能 → 规则。粒度控制到「一个可独立验证的行为」为止。

**Step 2｜抽取变量因子**
把需求里所有**可变的输入**列出来：等级、数量、时间、身份、网络状态、背包空间、是否首次……

**Step 3｜组合与裁剪**
- 单因子：等价类 + 边界值（0、1、最大、最大+1）
- 多因子：**判定表**（条件少）或**正交表/配对组合**（条件多），剔除不可能组合
- 别做全排列，会爆炸

**Step 4｜补齐“四个必加”**
> 异常流程 + 边界值 + 跨系统联动 + 非功能（弱网/并发/安全）

这四类是**漏测的重灾区**，也是新手和老手的差距所在。

**Step 5｜结构化输出**
用表，不用散文：

| 编号 | 模块 | 需求来源 | 测试点 | 类型 | 优先级 | 前置条件 | 关联系统 |
|---|---|---|---|---|---|---|---|
| TC-SIGN-001 | 签到 | 需求 3.2 | 当日第 2 次点击签到，提示"今日已签到"且不发奖 | 功能-逆向 | P1 | 已签到 | — |

**Step 6｜评审**
拉上策划（确认理解对不对）+ 开发（确认实现边界）+ 主测（查漏）。评审过的测试点，才进入写用例环节。

## 四、完整示例：把「邮件系统」拆开看

假设需求：*「系统邮件保留 30 天，附件可领取，背包满时无法领取，过期邮件自动删除。」*

| 维度    | 拆出的测试点（节选）                                                  |
| ----- | ----------------------------------------------------------- |
| 功能点   | 收件、已读/未读、领取附件、一键领取、删除、过期清理、红点、附件预览                          |
| 主流程   | 收到邮件 → 打开 → 领取 → 附件进背包 → 邮件变已领                              |
| 逆流程   | 已领再点领取、已删邮件、空附件邮件点领取、非本人邮件                                  |
| 边界    | 保留第 29 天 / 30 天 / 31 天；附件数量 0 / 1 / 上限 / 超上限                |
| 规则组合  | 背包**刚好满** / 满但该道具可堆叠 / 多附件部分能领部分不能 → 是否**部分成功**？（这里最容易吵）    |
| 状态迁移  | 未读未领 → 已读未领 → 已领 → 过期删除；跨状态直接跳                              |
| 联动    | 背包满 → 是否转邮件暂存？邮件又满 → ？仓库/摆摊/交易中的道具能否作为附件                    |
| 权限/身份 | 新号首封邮件、被封号、跨服角色、账号换绑                                        |
| 环境    | 跨时区（UTC+8 vs UTC-5）是否提前过期；弱网下领取；断线重连后状态是否一致                 |
| 非功能   | **连点领取是否重复发货**（经典刷道具 bug）；改本地时间；服务端与客户端时间不一致；1000 封邮件时的加载性能 |
| 生命周期  | 首次登录、跨天、跨周、跨版本更新后旧邮件是否还在、热更前后                               |

看到没——**“邮件满时附件怎么办”这种问题，光看需求文档是看不出来的，必须靠维度和经验去撞**。

## 五、优先级怎么分

| 级别     | 内容                    | 依据        |
| ------ | --------------------- | --------- |
| **P0** | 主流程、登录、支付、存档、发奖、数据一致性 | 挂了就上不了线   |
| **P1** | 分支流程、常见异常、核心联动        | 影响体验或可被利用 |
| **P2** | 极端边界、兼容性、性能、多语言       | 抽测 / 上线前扫 |

## 六、两个高阶技巧

**① 影响面倒推（回归测试点）**
不要只看新需求。问开发一句：*「这次改动动了哪些公共模块？」*
→ 改了背包接口 → 所有调用背包的系统（商城、任务、邮件、副本掉落、交易）全部进回归清单。**功能上线后炸老功能的，90% 是这里漏的。**

**② 需求追踪矩阵（RTM）**
一列需求、一列测试点、一列用例，做双向映射。上线前检查：**每条需求是否至少被 1 个测试点覆盖**。这是“需求覆盖率 100%”唯一能被证明的方式。

## 一、什么叫做"打包"

**打包（Build / Package）** 指把散落在工程里的代码、美术资源、配置表、音效、脚本、引擎和第三方 SDK，经过编译、压缩、合并、加密，最终产出一个**能装到真机或电脑上独立运行的产物**。

在编辑器里点 Play 能跑，和打包后能跑，是两件事。所以测试必须基于"包"：

- **环境差异**：编辑器里资源是散文件、代码是即时编译；包里资源被打成 AssetBundle/AB 或压缩包，代码可能走 IL2CPP/AOT、混淆、裁剪，路径、加载方式全变了。
- **真实的失败点**：漏资源、配置表没导出、依赖丢失、签名错误、渠道参数缺失、SDK 版本冲突、包体超限，**只有打包后才暴露**。
- **性能与内存**：真机上的渲染、内存峰值、加载耗时、发热耗电，编辑器数据没有参考价值。
- **平台能力**：权限申请、推送、支付、登录、剪贴板、后台切回，都要在真包上才成立。

常见的包类型（测试会接触到）：

| 类型 | 用途 | 特点 |
|---|---|---|
| Debug / Development Build | 开发自测、QA 定位问题 | 带日志、调试面板、性能分析，不能外发 |
| Release 包 | 提测、上线 | 关闭日志、开启混淆/裁剪 |
| 渠道包 | 各应用商店/平台 | 包名、签名、渠道号、SDK 不同 |
| 资源包 / 热更包 | 不发新包的前提下更新内容 | 只有资源+脚本+配置 |
| 整包（强更包） | 大版本 | 需要用户重新下载安装 |

打包流水线一般做的事：拉取指定分支 → 编译代码 → 构建资源 → 导出配置表 → 注入版本号/渠道号 → 签名 → 上传制品库 → 分发到测试人员。**包要有唯一版本号、构建号、Commit 记录**，否则出了 bug 说不清测的是哪个包。

## 二、内部开发 / 内部测试 / 内部灰度三个环境

先纠正一个常见误解：这三个不是"三套服务器随便选"，而是**同一条发布链路上的三道门，稳定性依次升高、变更频率依次降低、准入门槛依次升高**。

```
开发环境(dev) → 测试环境(test/QA) → 灰度环境(gray/staging) → 生产环境(线上)
   最不稳定          较稳定              最接近线上           真实用户
```

| 维度 | 内部开发环境 | 内部测试环境 | 内部灰度环境 |
|---|---|---|---|
| **主要使用者** | 程序、策划 | QA、开发 | QA、运营、少量内部/白名单用户 |
| **代码状态** | 随时提交，未提测 | 已提测的稳定分支 | 已封板的候选版本 |
| **稳定性** | 低，随时挂 | 中，功能可用 | 高，接近线上 |
| **数据** | 测试脏数据、可随意造 | 测试数据 | 接近生产的数据，慎改 |
| **配置/SDK** | 测试 AppID、沙箱支付 | 沙箱支付、测试推送 | 真实 SDK（沙箱/小额）、真实域名与 CDN |
| **变更频率** | 每天多次 | 按提测节奏 | 极低，只修阻断问题 |
| **出问题的影响** | 无所谓，重来 | 阻塞测试进度 | 影响发布决策，必须回滚 |
| **目的** | 联调、自测 | 功能验证、回归 | 验证线上真实表现、小范围放量 |

**关系**：代码/配置按 dev → test → gray 逐级"晋级"，每一级都是一道质量门禁；gray 通过后才允许放量到线上。环境之间要**物理隔离**（服务器、数据库、CDN、支付商户号、推送证书、域名都分开），否则会出现"测试数据打到线上""测试推送发给真实用户"这类事故。

**差别本质**：不是功能差别，而是**"离真实用户有多近"** 的差别。越靠近线上，越不允许有"我们改一下再看看"的自由，越依赖灰度、开关、回滚预案。

补充：很多团队还有**外网灰度**（线上小流量 1%~10%），它和"内部灰度"不是一回事——内部灰度是发布前的最后一道内部验证，外网灰度是已经上线后控制爆炸半径的手段。

## 三、为什么封板提审后只能靠热更

"封板"= 版本冻结，包体已构建、已签名、已提交平台审核。此时**包体是一个不可变的、已经离开你手里的产物**，原因有四层：

1. **二进制已经交出去了**。审核期间你改包 = 撤回重提，审核周期不可控（国内各渠道、iOS 各有排队），上线时间直接崩。而且用户设备上装的是那个二进制，你没法远程替换它。
2. **平台规则限制**。应用商店对"下发可执行代码改变 App 主要功能"有明确限制（苹果审核指南对此有约束，JSPatch 类方案曾被大规模下架）。所以热更的合法边界通常只有：**资源、配置表、脚本（在解释执行的合规范围内）、AB 包、活动内容**。
3. **原生层改不了**。新增权限、改包名、换引擎版本、升级原生 SDK、改启动流程、改签名——这些必须发新包。热更**碰不到原生代码**。
4. **成本与体验**。发新包意味着重新审核 + 用户重新下载 + 强制更新流失。相比之下，热更只下几十 MB 资源，用户无感。

所以结论是：**封板后能热更的只有"资源层和脚本层"的问题；碰原生、碰权限、碰合规的，只能等下一个版本。** 这也是为什么"这个 bug 能不能热更"必须由开发在修之前就判断清楚——判断错了，做完发现发不出去。

热更自身的风险也要清楚：老包兼容（用户可能停在 N-2、N-3 版本）、热更包本身的 bug 只能用"再热更一次"来修、回滚要提前设计。

## 四、热更测试流程，以及为什么要这么做

典型流程：

1. **问题/需求确认与可热更性判断**：确认改动范围，确认不涉及原生与合规红线。
2. **制作热更包**：资源/脚本/配置打包，生成版本号、清单文件、MD5、差异包。
3. **内部测试环境验证**：功能验证 + 影响面回归（改了 A 要回归依赖 A 的 B、C）。
4. **多版本升级路径测试（最关键的一步）**：从 N-1、N-2、更老版本分别升到最新；整包+热更组合；首次安装 vs 老用户升级。
5. **异常场景测试**：弱网、断网、下载中断点续传、中途杀进程、存储空间不足、下载到一半切后台、MD5 校验失败、CDN 异常、重复下载、跨版本跳更。
6. **灰度环境验证**：内部白名单用户真实设备跑一遍，看崩溃率、加载成功率、支付/登录。
7. **线上灰度放量**：1% → 5% → 20% → 50% → 100%，每档观察崩溃率、留存、付费、异常日志。
8. **全量或回滚**：指标异常立即停止放量并回滚到上一版本清单。

**为什么要这么麻烦：**

- 热更**直接触达线上真实用户**，没有"审核"这层缓冲，出错就是事故。
- 用户**版本碎片化**，升级矩阵是指数级增长的，不测老版本升级就一定有人升完打不开。
- 网络与设备环境不可控，下载类功能是事故高发区，必须专门构造异常。
- 出问题时**修复手段极少**（只能用新的热更去修上一个热更），所以只能靠灰度控制爆炸半径、靠回滚预案兜底。
- 热更包和整包是**两套制品**，容易出现"整包好的、热更坏的"这种只在升级路径上才复现的问题。

一句话：热更测试的重点不是"功能对不对"，而是**"在各种老版本、各种网络、各种中断下，用户能不能安全地升上来"**。

## 五、预习：怎么把需求拆成测试点

拆测试点不是"把需求抄一遍加个'验证'"，而是**把需求翻译成"可观察、可判定"的检查项**。给你一套可以直接用的方法。

### 第 1 步：先把需求读成三张清单

- **改了什么**：新增/修改/删除了哪些功能、界面、配置、数据字段。
- **影响谁**：哪些老功能依赖它（回归范围），哪些老数据/老存档会经过它。
- **验收标准**：策划/主程说"做成什么样算对"，没有就当场问。

### 第 2 步：用固定维度"扫"一遍，防止漏

| 维度 | 要问自己的问题 |
|---|---|
| 正常流 | 主流程一遍走通的最短路径是什么 |
| 异常/失败 | 断网、超时、服务器报错、重复点击、并发请求 |
| 边界 | 数值 0 / 1 / 上限 / 超上限、空列表、满背包、等级临界 |
| 状态与生命周期 | 登录前/后、切场景、切后台、断线重连、跨天、跨周 |
| 数据与兼容 | 配置表字段缺省、老存档、老版本升级、多语言 |
| 交互与 UI | 适配、遮挡、按钮置灰、连续点击、返回键 |
| 性能与资源 | 加载耗时、内存、包体、低端机 |
| 付费/运营 | 支付回调、补单、后台开关、活动时间 |
| 权限与合规 | 隐私授权、未成年人、实名 |

### 第 3 步：用设计方法补细节

等价类划分、边界值、判定表（多条件组合）、场景法（用户真实操作路径）、错误推测（凭经验猜哪里容易坏）、状态迁移（把功能画成状态机，每条边都是一个测试点）。

### 第 4 步：输出成清单，而不是散点

每个测试点写清：**编号｜模块｜前置条件｜操作｜预期结果｜优先级｜能否自动化｜关联需求**。测试点是"检查什么"，用例是"怎么点"，两者不要混。

### 动手练习（建议你今天就用这个练）

拿一个具体需求，比如 **"新增每日签到，连续 7 天领奖，断签重置"**，试着拆：

- 正常：首次签到、连续第 2~7 天、第 7 天领大奖、第 8 天重新循环
- 边界：第 7 天当天 23:59:59 签、次日 00:00:00 签、跨时区、服务器时间与客户端时间不一致
- 异常：断网签到、重复点击、签到请求超时后重试（会不会重复发奖）、背包满领不了奖
- 状态：签到中途退出重进、切后台跨天、断线重连后补签
- 数据：老用户第一次上线（无签到记录）、活动配置中途改奖励、配置表缺字段
- 兼容：老版本客户端没有签到入口、热更后入口出现
- 运营：后台改签到奖励/开关、活动下线
- 性能/UI：红点、按钮态、适配

拆完你会发现，**一个看起来 5 分钟的功能，能拆出 30+ 个测试点**——这就是拆解能力的体现。练 3~5 个需求后，你会形成自己的检查清单，速度会快很多。
