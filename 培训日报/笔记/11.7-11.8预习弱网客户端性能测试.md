# 一、弱网

## 1. 为什么需要弱网测试

真实用户并不总在“公司 Wi-Fi + 满格 5G”里使用 App：

| 现实场景 | 表现 |
|---|---|
| 地铁、电梯、地下车库 | 信号弱、频繁切换基站、丢包、闪断 |
| 高铁、高速公路 | 小区切换密集、RTT 抖动大 |
| 演唱会、展会 | 拥塞、带宽骤降、上行几乎不可用 |
| Wi-Fi 与 4G 互切 | 连接中断、IP 变化、长连接断开 |
| 弱网 + 锁屏/切后台 | 进程被挂起、socket 被回收 |
| 运营商 NAT 超时 | 长连接静默失效，推送延迟 |

不测弱网的典型后果：

- **功能层面**：请求超时后无兜底 → 白屏、一直转圈、重复提交、订单状态不一致、支付掉单。
- **稳定性层面**：超时重试风暴、连接泄漏、ANR、崩溃、OOM。
- **体验层面**：首屏 10s、图片半张、视频卡死、按钮点了没反应。
- **成本层面**：无节制重试导致流量和电量暴涨。

一句话：**弱网测试是在验证“网络不可靠”这个前提下的容错设计**，而不是验证功能对不对。

## 2. 底层原理：弱网到底“弱”在哪

弱网不能简单理解成“网速慢”。它其实是**协议栈多层问题的叠加**，至少要理解下面几层：

### （1）无线链路层：丢包和抖动是“物理必然”

- 信号质量用 **RSRP/SINR** 衡量，基站根据它动态选择 **MCS（调制编码方案）**。信号差 → 低阶调制 → 速率低、误块率高。
- **HARQ（L1/L2 重传）** 和 **RLC ARQ** 会重传错误块，表现为**延迟抖动 + 突发丢包**，而不是均匀丢包。
- **PDCP 重排序**：切换或重传会导致包乱序，TCP 会误判为丢包。

所以模拟弱网时，**“固定 10% 丢包”并不真实**，真实弱网是“成串丢包 + 抖动 + 速率突变”。

### （2）RRC 状态机：移动网络有“额外的唤醒成本”

手机不是一直保持连接态：

- `Idle → Connected` 需要 **RRC 建立 + 随机接入**，通常多出 **100~500ms**。
- 连接态空闲一段时间（Tail Time，常见 5~10s）才释放。释放后再发请求，又要重建。
- 这解释了为什么“隔一会儿点一下”比“连续操作”更慢。

### （3）切换（Handover）：几十毫秒的“黑洞”

测量上报 → 切换命令 → 随机接入新小区，期间可能**中断几十毫秒并丢包**。高铁场景尤其明显。**连接迁移能力**（QUIC 的 Connection ID）就是为这个设计的。

### （4）TCP 层：弱网性能主要由拥塞控制决定

这是最核心的一层：

| 机制 | 弱网下的问题 |
|---|---|
| 三次握手 | 1 个 RTT 才能发数据；RTT 500ms 就是 500ms |
| 慢启动 | 初始 cwnd 约 10 MSS，每 RTT 翻倍；高 RTT 下爬升极慢 |
| 丢包重传 | 快速重传要 3 个重复 ACK；否则等 **RTO**（Linux 最小 200ms，指数退避） |
| 拥塞控制 | Reno/CUBIC 丢包即减半；**BBR** 基于带宽时延积，弱网表现更好 |
| 队头阻塞 | 一个包丢了，后续包即使到了也要等重传 |
| 吞吐上限 | 吞吐 ≈ `cwnd / RTT`，高 RTT 下窗口不够就是上不去 |
| NAT 超时 | 运营商 NAT 表项 5~30 分钟过期，长连接“假在线” |

**带宽时延积（BDP）= 带宽 × RTT**。高 RTT 场景要足够大的窗口才能跑满带宽，这也是为什么“限速 1Mbps + RTT 800ms”比“限速 1Mbps + RTT 20ms”难得多。

### （5）DNS / TLS：连接建立前的“隐藏成本”

- DNS 走 UDP，超时通常 **5s 起**，多个 nameserver 串行重试；移动网络 DNS 经常很慢。
- TLS 1.2 握手 **2-RTT**，TLS 1.3 **1-RTT**（0-RTT 有重放风险）。
- 所以一个请求的真实耗时 = DNS + TCP + TLS + 请求 + 响应，弱网下**建连开销可能远大于传输开销**。

### （6）HTTP 层

- HTTP/1.1：队头阻塞 + 浏览器/客户端 6 连接上限 → 并发请求排队。
- HTTP/2：应用层多路复用，但**底层仍是 TCP，TCP 丢包照样队头阻塞**。
- HTTP/3/QUIC：基于 UDP，用户态实现，**解决 TCP 层 HOL、支持连接迁移、0-RTT**。

### （7）MTU / 分片

移动网络 MTU 常为 1400~1500，VPN 下更小。**PMTUD 黑洞**会导致大包（上传、POST body）卡死，小包正常，这类问题极难排查。

### 弱网参数的正确建模

| 维度 | 典型取值 |
|---|---|
| 时延 RTT | 100ms / 300ms / 800ms / 2s |
| 丢包 | 1% / 5% / 10% / 20%（建议成串丢包） |
| 抖动 jitter | ±50ms / ±200ms |
| 带宽 | 下行 50kbps~2Mbps，**上下行不对称**（上行常更差） |
| 乱序/重复 | reorder 1~5%，duplicate 1% |
| 闪断 | 断 3s / 10s 后恢复 |
| 完全断网 | 飞行模式、DNS 失败、连接拒绝 |
| 服务端慢 | 响应延迟 3s、5xx、超时 |

## 3. 怎么做：工具 + 场景 + 判据

### （1）工具分层

| 层次 | 工具 | 能力 |
|---|---|---|
| 系统级 | **iOS/macOS Network Link Conditioner** | 预设 3G/Edge/LTE/100% Loss，改 delay/loss/bandwidth |
| 系统级 | **Android Emulator** 网络参数 | speed/latency，适合粗测 |
| 系统级 | **Linux `tc` + `netem`** | delay/jitter/loss/corrupt/reorder/duplicate/rate，最灵活 |
| 系统级 | **clumsy**（Windows，WinDivert） | lag/drop/throttle/duplicate/out-of-order |
| 代理级 | **Charles / Fiddler / mitmproxy** | 限速、断点、Map Remote、Rewrite、注入延迟/错误码；mitmproxy 可写脚本做**可编程故障注入** |
| 平台级 | **Facebook ATC**、腾讯 **QNET**、**WeTest 云真机** | 多机集中管理、真实设备弱网 |
| 物理级 | 屏蔽箱 + 可调衰减器 | 最接近真实射频环境 |

> 建议组合：**代理层做“应用层故障注入”**（超时、5xx、慢响应、DNS 失败），**系统层做“链路层弱网”**（延迟、丢包、限速、闪断）。两者不等价。

### （2）场景矩阵（不要只测“慢”）

- **网络制式**：2G / 3G / 4G / 5G / Wi-Fi / Wi-Fi 弱信号
- **参数组合**：高延迟、丢包、抖动、限速、闪断、完全断网、DNS 失败
- **关键业务流**：启动 → 登录 → 首页 → 列表 → 详情 → 图片/视频 → 搜索 → 下单/支付 → 上传 → IM 收发 → 推送
- **系统事件**：切前后台、锁屏、来电、Wi-Fi↔4G 切换、飞行模式开关、低电量模式
- **长连接**：心跳、断线重连、消息乱序/重复/补拉
- **极端组合**：弱网 + 杀进程、弱网 + 高频点击、弱网 + 支付、弱网 + 后台恢复

### （3）判据（可量化）

| 指标 | 期望 |
|---|---|
| 请求成功率 | 弱网下不低于基线（如 ≥95%） |
| P95 响应时间 | 有明确上限，超时时间可预期 |
| 崩溃/ANR/OOM | **0** |
| 白屏/无限 loading | 不超过 N 秒，必须有兜底 UI |
| 重试次数 | 有上限、有退避、只对幂等请求重试 |
| 数据一致性 | 不重复下单、状态最终一致 |
| 流量 | 无重复请求、无重试风暴 |
| 恢复能力 | 网络恢复后自动刷新/补拉/断点续传 |

### （4）客户端该怎么做（工程对策）

1. **超时分级**：连接超时、读写超时、总超时分开设，不要一个 30s 全局超时。
2. **重试策略**：指数退避 + 随机抖动（jitter），限制次数，仅幂等请求可重试，避免“重试风暴”。
3. **幂等设计**：客户端生成幂等 ID，服务端去重，支付/下单必须防重复。
4. **缓存与降级**：HTTP 缓存/ETag、本地缓存、骨架屏、弱网自动降级（低清图、关自动播放）。
5. **连接优化**：DNS 预解析、预连接、连接池、HTTP/2、QUIC/HTTP3。
6. **弱网探测**：基于 RTT/成功率动态调整策略（超时、并发、图片质量）。
7. **断点续传**：分片 + 校验 + 续传，上传下载都要。
8. **长连接保活**：心跳 + 网络变化监听 + 退避重连 + 消息补拉。
9. **用户可感知**：明确的 loading、超时提示、重试按钮，不要“静默失败”。

# 二、客户端性能测试

## 1. 为什么

- **用户感知直接决定留存**：启动慢 1s、滑动掉帧、手机发烫，用户就走了。
- **设备碎片化严重**：低端机、老系统占比高，高配机上“没问题”不等于没问题。
- **资源受限**：CPU、内存、GPU、电量、流量、存储都是硬约束。
- **质量问题会放大**：内存泄漏 → OOM；主线程阻塞 → ANR；过度绘制 → 发热耗电。
- **需要质量门禁**：版本迭代要有基线、有回归、有线上监控，否则性能会“温水煮青蛙”式退化。

## 2. 指标体系（按维度）

| 维度 | 核心指标 | 说明 |
|---|---|---|
| **启动** | 冷启动/温启动/热启动耗时、首帧时间、首屏可见、TTID/TTFD、可交互时间 | 冷启动最接近用户真实体验 |
| **流畅度** | FPS、帧耗时 P90/P99、掉帧率、jank 率、Slow Frame(>16ms)、Frozen Frame(>700ms) | 看**分位数**，不看均值 |
| **内存** | PSS 峰值、Java/Native 堆、GC 次数与停顿、泄漏、OOM 率 | PSS 比 RSS 更贴近实际占用 |
| **CPU** | 占用率、主线程 CPU、线程数、方法耗时、锁竞争 | 主线程阻塞是卡顿根因 |
| **网络** | 流量、请求数、包大小、DNS/建连耗时 | 与弱网测试联动 |
| **电量/温度** | 电流、mAh、温升、WakeLock 时长、后台唤醒 | 发热会触发降频，反过来影响流畅度 |
| **稳定性** | 崩溃率、ANR 率、卡死、Native Crash | 性能测试的“一票否决”项 |
| **包体/存储** | APK/IPA 大小、So 大小、磁盘占用、缓存 | 影响下载转化和存储焦虑 |
| **渲染** | 过度绘制、布局层级、GPU 耗时 | 影响掉帧和发热 |

## 3. 怎么做：完整流程

### Step 1：定基线与 SLA

先明确“多少算好”：冷启动 < 1.5s、滑动 FPS ≥ 55、P95 帧耗时 < 16.7ms、内存峰值 < 300MB、崩溃率 < 0.1%……**没有基线的性能测试没有意义**。

### Step 2：设备矩阵

| 档位 | 示例 | 目的 |
|---|---|---|
| 低端 | 4 核 / 2~3GB / Android 8~10 | **最容易被忽略、问题最多** |
| 中端 | 主流千元机 | 主力覆盖 |
| 高端 | 旗舰 | 对照基线 |
| iOS | iPhone SE/8（老机型）+ 新款 | 覆盖老设备 |

同时覆盖不同系统版本、不同屏幕分辨率/刷新率（60Hz vs 120Hz）。

### Step 3：场景脚本

- 冷启动（清进程、清缓存）
- 首页 → 列表滑动（长列表、图片流）
- 页面反复跳转（路由、内存增长）
- 图片/视频加载
- 搜索、输入、动画
- 后台驻留、切前后台循环
- 长时间使用（内存泄漏、温升）

用 **UI 自动化**（Appium/UIAutomator/XCUITest/Maestro）保证可重复，避免手测抖动。

### Step 4：采集工具链

**Android**

| 目标 | 工具 |
|---|---|
| 启动耗时 | `adb shell am start -W`、Macrobenchmark、Perfetto |
| 帧率/卡顿 | `dumpsys gfxinfo`、`gfxinfo framestats`、JankStats、Perfetto/Systrace |
| 方法耗时 | Studio Profiler、Simpleperf、Trace、火焰图 |
| 内存 | Profiler、`dumpsys meminfo`、LeakCanary、MAT |
| 电量 | Battery Historian、Energy Profiler |
| 布局 | Layout Inspector |
| 线上 | Matrix、Bugly、APMPlus |

**iOS**

| 目标 | 工具 |
|---|---|
| 启动 | Instruments App Launch、XCTest Metrics、MetricKit |
| 卡顿 | Core Animation、CADisplayLink、Time Profiler |
| 内存 | Allocations、Leaks、VM Tracker |
| 电量 | Energy Log |
| 线上 | MetricKit、Sentry、Firebase Performance |

**跨端**：Flutter DevTools（Frame Chart、Memory）、React Native Performance Monitor、小程序测速面板。

### Step 5：分析

- **看分位数**：P50/P90/P95/P99，均值会被长尾掩盖。
- **看趋势不看单点**：多轮取中位数，排除温升/后台干扰。
- **归因到代码**：trace/火焰图定位到方法；帧耗时定位到 measure/layout/draw 哪一段。
- **对比基线**：版本间、机型间、竞品间。

### Step 6：优化 → 回归 → 线上监控

性能是**持续工程**：CI 里跑 Macrobenchmark 做门禁，线上用 APM 采集真实用户数据（RUM），形成“发现—定位—修复—验证”闭环。

## 4. 底层原理：为什么这样测、这样优化

### （1）渲染：16.67ms 的硬预算

```
VSync(16.67ms@60Hz) → Choreographer 回调
  → input / animation / traversal
  → measure → layout → draw（UI 线程）
  → RenderThread 同步 → GPU 绘制
  → SurfaceFlinger 合成 → 送显
```

- 一帧超过 16.67ms 就**掉帧**；120Hz 屏幕只有 8.33ms。
- **双缓冲/三缓冲 + BufferQueue**：生产者（App）与消费者（SurfaceFlinger）解耦，但缓冲满时 App 会被阻塞。
- 掉帧根因通常三类：**主线程被占**（IO、锁、计算）、**布局层级过深/过度绘制**、**GPU 上传纹理慢**（大图、圆角、阴影）。
- 卡顿检测原理：**Looper Printer**（消息前后打点，超阈值打印堆栈）、**Choreographer.FrameCallback**、**FrameMetrics**、BlockCanary 都是这个思路。

### （2）内存：为什么 PSS 会涨、为什么 OOM

- Android 进程内存 = Java Heap + Native Heap + Code + Stack + Graphics。
- **GC**（ART 的 Concurrent Copying GC）会 STW 暂停，**内存抖动**导致频繁 GC → 卡顿。
- **内存泄漏**：长生命周期对象持有 Activity/Context → 无法回收 → 堆涨 → OOM。
- **LMK（Low Memory Killer）** 按 `oom_adj` 杀进程；iOS 对应 **Jetsam**。所以“内存高”不只是 OOM，还会导致**后台被杀、冷启动变多**。

### （3）启动：为什么冷启动慢

```
zygote fork → Application.attachBaseContext → onCreate
  → Activity onCreate/onStart/onResume
  → ViewRootImpl.performTraversals → 首帧上屏
```

主要耗时：**类加载/dex2oat**、**Application 初始化（三方 SDK）**、**资源解析**、**布局 inflate**、**首帧绘制**。优化手段：启动器任务编排、懒加载、IdleHandler、启动窗口（Splash）、基线 Profiles、AOT。

### （4）CPU 与功耗

- **big.LITTLE + EAS 调度**：任务放错核、频繁升频都费电。
- **DVFS**：发热 → 降频 → 掉帧，所以性能测试要**跑够时长**看温升后的表现。
- **WakeLock / Alarm / 定位** 是后台耗电大户；Doze 模式会限制后台任务。

### （5）测量原理：采样 vs 插桩

- **采样**（perf/Simpleperf）：开销小，适合线上/长跑，但可能漏短函数。
- **插桩**（Trace/Systrace/Perfetto）：精确，但有开销，适合离线定位。
- **ftrace / 硬件性能计数器**：内核态与 CPU 事件级观测。
- 统计口径要统一：冷/热启动、是否清缓存、Debug/Release 包、是否连充电器（影响调频）。

## 5. 常见坑

1. 只看均值，不看 P95/P99。
2. 只在高配机测，低端机“上线才爆”。
3. 用 Debug 包测性能（Debug 有额外开销，数据失真）。
4. 不控变量：后台应用、温度、电量、网络都在变。
5. 样本太少、单次结论。
6. 忽略**温升降频**和**长时间运行**。
7. 弱网只测“延迟”，不测丢包/抖动/闪断。
8. 忽略后台/多进程/长连接。
9. 没有基线、没有回归门禁，性能逐版本退化。

# 三、面试速答版（一句话总结）

- **弱网为什么**：真实网络不可靠，要验证超时、重试、降级、一致性等容错设计。
- **弱网原理**：无线链路丢包抖动 + RRC 状态切换 + TCP 拥塞控制/RTO/队头阻塞 + DNS/TLS 建连开销 + NAT 超时。
- **弱网怎么做**：系统层（netem/NLC/clumsy）+ 代理层（Charles/mitmproxy）注入延迟/丢包/限速/闪断/错误码，按“制式 × 参数 × 业务 × 系统事件”矩阵测，用成功率/P95/崩溃/白屏/一致性做判据。
- **性能为什么**：资源受限 + 设备碎片化 + 用户感知直接关联留存，需要基线、回归和线上监控。
- **性能怎么做**：定基线 → 设备矩阵 → 自动化场景 → 工具采集（启动/帧率/内存/CPU/电量）→ 分位数分析 + trace 归因 → 优化回归 → APM 线上监控。
- **性能原理**：16.67ms 渲染预算与 VSync/Choreographer、GC 与 LMK/Jetsam、启动链路（zygote→Application→首帧）、DVFS 与 WakeLock、采样 vs 插桩。
